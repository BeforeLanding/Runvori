# Runvori · 续行 PRD

版本：v0.1 需求基线。日期：2026-10-23。状态：待实现、待验证。

依据：[定位与首版方案](定位与首版方案.md)。本 PRD 将既有定位展开成可开发、可验收的需求；其中数字是首轮验收目标，不是已有测量结果。

## 1. 产品与用户

Runvori 让开发者离开电脑后，在 Android 手机上查看自己启动的 Codex 工作、处理审批、检查改动和验证结果。执行始终发生在开发电脑，手机提供受限的查看与控制入口。

首要用户是已经使用 Codex CLI 的个人开发者：在可信开发电脑上启动短时修复/开发任务，临时离席，仍希望知道任务是否卡住、是否需要自己决定、最终是否有验证证据。首版不面向组织级管理或无人值守生产运维。

核心问题是移动端长输出难读、审批状态在网络异常下不可信、重新打开后丢失上下文，以及“模型说完成了”与“真实命令通过了”混淆。首版价值由这些问题的实测结果证明，见 [测试计划](TEST_PLAN.md)。

## 2. 目标和范围

首版必须能演示：电脑启动任务 → 手机读进度 → 审批 → 断网重连 → 检查差异和命令结果 → 在同一历史会话开始新回合。

固定范围：

- Kotlin＋Jetpack Compose Android 客户端。
- Python＋FastAPI＋SQLite Host，通过 stdio 连接 Codex app-server。
- 一台 Host、一台配对手机、全局最多一个非终态回合；不建立任务队列。
- Host 本地登记工作区并启动首个会话；手机可对该会话发起后续回合。
- HTTPS、可信局域网或已有 VPN、设备配对；模型认证与凭据留在电脑。
- 仅管理 Runvori 启动和登记的会话，不扫描、接管其他 Codex 会话。

不进入 v0.1：iOS/Web 客户端、公网中继、云账户、多设备/多用户、多 Agent、任意终端/PTY、远程文件管理、RAG/项目记忆、GUI 自动化、自动提交/推送/合并/部署、任务调度、后台常驻连接及推送到达保证。

## 3. 名词与状态

- 工作区：Host 本地登记的规范化目录，绑定执行策略。
- 会话 `session`：一个工作区中的 Runvori 对话，映射一个 Codex thread。
- 回合 `run`：一次用户输入及其执行，映射一个 Codex turn；“任务”在界面中指该回合。
- 事件 `event`：Host 已持久化、按会话序号排列的事实记录。
- 审批 `approval`：上游正在等待的特定请求及其处理记录。
- 产物 `artifact`：受限的命令输出或差异等内容；其来源、截断状态必须可见。

回合状态使用 `starting / running / waiting_approval / interrupting / completed / failed / interrupted`。连接状态单独使用 `online / reconnecting / offline / unauthorized / incompatible`。审批和验证有独立状态，详见 [协议](PROTOCOL.md)；断网不能把回合改成失败，回合完成不能把测试改成通过。

## 4. 使用流程

### 首次准备

开发者在电脑安装兼容 Codex、完成登录、登记测试工作区、启动 Host，完成本地健康检查后生成短时配对信息。手机扫描信息，核对 Host 身份并通过 HTTPS 配对。首次任务在电脑本地发起，绑定工作区、审批策略和验证命令清单。

### 离席接管

手机打开会话看到 Host 最近确认的回合状态、更新时间和时间线。浏览历史时，新增输出不改变阅读位置；用户可主动回到最新。审批显示真实操作、范围和原因，提交后进入“处理中”，以 Host 确认的状态为准。用户可请求中断当前回合。

### 恢复与结束

断网时继续读缓存，所有写操作禁用；重连先同步事件和审批，再开放操作。手机进程重建后恢复会话和阅读锚点。任务结束页展示回合状态、代码差异、命令、退出码和验证结论。若历史 thread 可加载且无活动回合，用户可以明确发送后续输入，建立新回合。

## 5. 功能需求

### FR-01 Host 准备、配对与撤销（P0）

- Host 在本地展示运行状态、兼容性、工作区和配对入口；具体 CLI 命令在实现后写入贡献指南。
- 配对使用短时、一次性秘密，手机校验 Host TLS 身份。首版最多一个有效设备；更换手机需在 Host 本地撤销原设备。
- 撤销后旧凭据的读写请求均被拒绝；不得通过重装客户端自动获得新授权。
- 验收：AT-01、AT-12。

### FR-02 会话与回合管理（P0）

- 本地在登记工作区创建会话和首回合；手机可查询会话列表、回合记录及快照。
- 列表显示标题、工作区别名、最近状态、待审批数和最近更新时间；使用游标分页。
- 非终态回合占用全局活动槽；重复请求和并发请求不能创建第二个执行。
- 验收：AT-02、AT-08。

### FR-03 事件时间线与稳定阅读（P0）

- 区分用户输入、Agent 文本、命令、文件改动、审批和系统异常；不把全部输出拼成不可分页的大字符串。
- 自动跟随最新和浏览历史为两种模式；用户离开末尾后保留可见条目与偏移，显示新增提示。
- 分页、批量刷新、长文本/代码换行、复制和“回到最新”可用；大型输出按块或产物读取，截断必须明示。
- 验收：AT-03、AT-11。

### FR-04 单次审批（P0）

- 首版覆盖兼容版本实际发出的命令执行和文件修改审批；显示操作内容、cwd/路径、原因和适用范围。
- 只提供本次允许/拒绝，不提供会话永久允许、策略扩权或全局免审。
- 显示提交中、等待上游确认、已处理、已失效、结果不确定；不可把 HTTP 接收成功当成执行成功。
- 重复点击、冲突决定、过期请求、响应丢失均返回可理解结果。未知审批种类不得默认允许，安全中断并解释不支持。
- 验收：AT-04、AT-05、AT-06。

### FR-05 中断当前回合（P0）

- 在线且状态新鲜时可请求中断；确认界面说明已产生的文件改动不会回滚。
- 请求接收后显示“正在中断”，只有终态事件或确定的执行中断记录才显示“已中断”。
- 终态竞争时显示最终真实状态；中断失败/不确定时可以刷新，不能默认显示成功。
- 验收：AT-07。

### FR-06 断线、后台与进程重建恢复（P0）

- 缓存最近会话、事件游标和阅读位置，区分最后同步时间与当前在线状态。
- 按序补齐已持久事件，重复事件不重复展示；遇到缺口停止前进并重新同步。
- 返回前台、旋转屏幕和客户端进程重建后恢复视图；后台不承诺及时收到审批，执行由 Host 保持。
- 离线不排队发送审批、后续输入或中断。曾发送但确认丢失的操作，重连后按原请求标识查询。
- 验收：AT-09、AT-10、AT-11。

### FR-07 差异与真实验证结果（P0）

- 展示回合相关文件改动、命令、cwd、开始/结束时间、退出码和输出入口；缺失信息显示未知。
- 预先登记的必需验证命令分别显示 `pending/running/passed/failed/unknown/not_run`。全部必需项真实退出码为 0 且证据完整时才汇总为通过。
- 未配置验证、测试未运行、执行被中断和证据不完整都不能显示“验证通过”。Agent 摘要单独标记。
- 回合内改动与工作区已有改动分别标明来源；无法准确分离时显示工作区差异及局限。二进制和超大文件可降级为元信息。
- 验收：AT-13、AT-14。

### FR-08 历史会话继续新回合（P0）

- 仅无活动回合且历史 thread 成功加载时开放后续输入；绑定原工作区和策略。
- 用户明确发起后创建新的 `run_id`，保留旧回合结果；未完成回合不能因重连自动重启。
- thread 不可用或工作区丢失时提示回到电脑处理；首版不导入其他 thread、不自动新建会话代替。
- 验收：AT-15。

### FR-09 Host/执行进程中断处理（P0）

- Host 重启或 app-server 意外退出后，先核对受管子进程并阻止新执行，将无法继续的非终态回合记录为中断，保留原因和最后已持久事件。
- 旧进程已终止/隔离且活动槽安全释放后，才允许用户明确开始新回合；旧审批失效，不重放批准。
- 保证已提交记录可读；不保证崩溃瞬间尚未落盘的上游输出可恢复，不宣称执行进程无损续跑。
- 验收：AT-16。

### FR-10 诊断与数据管理（P0）

- 提供 Host/客户端版本、协议版本、配对状态、最后同步和受限诊断信息；不包含模型凭据。
- 数据默认留在 Host 与配对手机；无第三方分析或自动上传。Host 本地可删除已终态会话，客户端可清除缓存/解除配对。
- 保留活动记录；存储不足时拒绝新回合并安全停止当前执行，明确说明原因，不能默默丢事件。
- 验收：AT-12、AT-17。

## 6. 非功能需求

### NFR-01 一致性与可解释性

已持久事件重放无缺漏/重复；快照和游标一致；审批最多接受一个决定，结果不确定不推断为成功；单活动回合约束在并发和重启下有效。自动化测试须覆盖所有故障切入点，不以 UI 防抖代替服务端保证。

### NFR-02 安全与隐私

所有手机请求认证，配对入口例外但受短时秘密和限流保护；只接受 HTTPS。凭据、私钥不进代码/日志/诊断包。远端只读登记工作区的受控产物，不接受任意路径或任意命令。详细边界见 [SECURITY.md](../SECURITY.md)。

### NFR-03 可用性与可访问性

关键状态不只依赖颜色；审批按钮有完整文字与朗读标签；系统字体放大至 200% 时仍能读取和操作。历史阅读不会因输出增长被拉走；离线与未知结果有明确文案。

### NFR-04 首轮性能目标

以 M0 冻结的 60 Hz Android 实机及 release 构建为基线：10,000 条、合计约 20 MiB 的脱敏事件，持续 20 条/秒追加时，滚动帧耗时 p95 ≤32 ms，卡顿帧比例 ≤5%，内存 PSS 峰值 ≤250 MiB。静态阅读锚点在追加/批量刷新后仍为同一条目，偏移误差 ≤8 dp。

可信局域网 RTT ≤50 ms、落后 1,000 条小事件（每条约 1 KiB）时，重连至游标追平并刷新审批的耗时 p95 ≤3 秒；Host 接收审批至本地返回已受理 p95 ≤500 ms，不包含模型和上游执行耗时。每项至少 20 次测量，性能方法见测试计划；M0 可依据基准修订，必须记录理由，不能只为通过而降低门槛。

## 7. 发布与成功判定

v0.1 候选版须满足：

- FR-01～FR-10 的自动化/手工验收完成，NFR 的数据与设备条件有记录。
- 审批错误放行、跨工作区读取、事件丢失、双活动回合、重启误报继续执行等阻断缺陷为零。
- 固定可重置演示仓库上，完整链路连续成功 10 次；成功、验证失败、主动中断、Host 重启均可复现。
- 交付可安装 APK、可启动的 Host 包、精确兼容清单、安装/配对/撤销/恢复说明和脱敏证据。
- 六周版本优先完成正确性闭环；性能整理与展示可用第七至八周完成。未通过发布门槛的版本只能称内部预览版。

## 8. 依赖与未决事项

依赖兼容 Codex CLI、用户已可用的模型访问、可达的 HTTPS Host 以及测试设备。首发 Host 操作系统、CLI 精确版本、Android 最低版本、构建组合及大差异采集方案在 M0 实测后确认，见 [DECISIONS.md](DECISIONS.md)。实现不能把这些待验证项写成支持承诺。
