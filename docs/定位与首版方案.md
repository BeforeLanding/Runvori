# Runvori 定位收敛与首版方案

> 文档日期：2026-10-23。本文记录项目定位与计划，所述功能及验收指标不代表已实现或已通过验证。

## 1. 结论：聚焦“离开电脑后，继续处理 Coding Agent 任务”

建议收窄当前定位。“可恢复的移动端 Agent 工作台”适合作为技术方向，但作为首版产品，用户、任务和使用时机还不够具体。

结合已经确定的 **Android 原生客户端、Codex CLI、Runvori Host 专属会话**，推荐定位为：

> **Runvori · 续行：让开发者离开电脑后，仍能在手机上查看 Codex 任务、处理审批、检查执行结果。**

围绕一个完整场景设计首版：

1. 开发者在电脑上通过 Runvori 启动一个修复或开发任务。
2. 离开电脑后，在手机上查看进度和代码变更。
3. Agent 请求执行命令或修改文件时，在手机上审批。
4. 手机断网、切换后台后，重新打开能恢复任务视图。
5. 任务结束后，检查改动、验证命令和退出状态。

**聚焦一个问题，不代表只实现一个功能。** 审批、流式输出、断线恢复和结果检查，都是这个场景需要的组成部分。

## 2. 两个参考项目带来的判断

### Agent OS：功能较多，但服务于同一条软件交付流程

[Agent OS](https://github.com/earthwalker17/agent-os) 围绕个人开发者的软件项目组织规划、执行、验证、恢复和交付。它将负责规划和记忆的 Main Agent，与在项目工作区执行任务的 Coding Agent 分开，功能扩展具有统一的业务主线。[架构说明](https://github.com/earthwalker17/agent-os/blob/59833d3f436bd1fd842860af2aa1c081d4b20363/ARCHITECTURE.md)

值得借鉴的是：

- **任务有可检查的记录**：事件、状态、结果和验证产物分开保存。
- **恢复有明确边界**：失败分类、重试预算和人工确认有独立规则。
- **状态正确优先**：运行卡片采用轮询，也能处理取消和结束状态，不必为了技术展示强行使用复杂传输机制。[运行卡片实现](https://github.com/earthwalker17/agent-os/blob/59833d3f436bd1fd842860af2aa1c081d4b20363/frontend/src/components/RunChatCard.tsx)

一个关键细节：其启动恢复逻辑会把遗留的运行中任务标记为失败，并记录中断原因。这属于恢复状态一致性，不能据此宣称“执行进程可以从中断位置继续”。[任务存储实现](https://github.com/earthwalker17/agent-os/blob/59833d3f436bd1fd842860af2aa1c081d4b20363/backend/execution/run_store.py)

**对 Runvori 的启发：采用任务、事件、产物的组织方式；首版范围控制在移动接管，不同时建设规划器、项目记忆和部署平台。**

### ProGhostty：围绕终端阅读体验，深入客户端工程

[ProGhostty](https://github.com/freecodetiger/ProGhostty) 是原生 macOS 终端，采用 Swift、AppKit、PTY 和 Ghostty VT 等组件。它复用终端底层能力，将工程投入放在原生交互与输出体验上。[构建配置](https://github.com/freecodetiger/ProGhostty/blob/698693f3ea879f49cce8be9bb20bdf42fac6ebaf/Package.swift)

对 Runvori 最有价值的是一个具体问题：

> Agent 持续输出时，用户正在阅读的历史位置应保持稳定，并能主动回到最新输出。

它把跟随最新输出与浏览历史分开处理，并为输出增长、滚动锚点和边界情况编写了回归测试；架构脚本还限制了 UI 框架进入核心层。[滚动测试](https://github.com/freecodetiger/ProGhostty/blob/698693f3ea879f49cce8be9bb20bdf42fac6ebaf/Tests/ProGhosttyCoreTests/SmoothScrollBrowseResolverTests.swift)、[架构检查](https://github.com/freecodetiger/ProGhostty/blob/698693f3ea879f49cce8be9bb20bdf42fac6ebaf/scripts/check-architecture.sh)

**对 Runvori 的启发：复用 Codex 的执行能力，把移动端的长内容阅读、审批和恢复做扎实。** 终端模拟器、VT 解析和 Metal 渲染不属于首版需求。

以上结论来自文档与源码静态核查，未运行两个项目验证其性能或实际可靠性。

## 3. 首版范围与职责划分

**Android：Kotlin＋Jetpack Compose**

负责任务列表、事件时间线、代码差异、审批卡片、取消操作、本地缓存，以及前后台切换和断网后的视图恢复。

两个重点客户端亮点：

- **持续输出下的稳定阅读**：历史位置保持、分页加载、批量刷新、明确的“回到最新”入口。
- **可靠审批与恢复**：重复点击、请求过期、确认丢失和重新连接都有明确反馈。

**Runvori Host：Python＋FastAPI＋SQLite**

运行在开发电脑上，通过 stdio 连接 Codex app-server，保存事件和任务快照，并向手机提供经过认证的访问接口。Codex 官方将 app-server 用于自定义客户端，提供线程、回合、事件及审批能力。[官方说明](https://developers.openai.com/blog/codex-as-a-platform)

最小接口覆盖：

- 查询会话和任务快照。
- 按事件序号获取增量更新。
- 查询并响应待处理审批。
- 中断当前回合。
- 获取差异、命令结果及产物。

首版固定为 **一台 Host、一台配对手机、一个活动回合**。通过 HTTPS 在可信局域网或既有 VPN 内访问，使用配对凭证；模型凭据留在电脑端。

只管理 Runvori 启动的会话。任意已有终端接管、多 Agent 调度、RAG、GUI 自动化和公网中继暂不进入首版。

## 4. 差异化与验收标准

官方 [Codex Remote](https://developers.openai.com/blog/mastering-codex-remote-for-engineering) 已覆盖手机查看任务和处理审批。因此，“手机控制 Codex”本身不足以构成独特卖点。

对求职目标，更有价值的项目主张是：

> **把移动端阅读、审批一致性和连接恢复做成有测试、有测量、有演示证据的工程项目。**

验收围绕四类场景展开：

- **阅读**：持续追加大量事件时，阅读历史不跳动；记录帧耗时、内存和恢复耗时。
- **连接**：断网、切换后台、旋转屏幕、客户端进程重建后，事件不漏、不重复，审批状态正确。
- **审批**：覆盖重复提交、审批已失效、服务端已接收但手机未收到确认；以 Host 和 Codex 的状态为准。
- **执行**：覆盖成功、测试失败、主动中断和 Host 重启。展示真实命令及退出码，避免把模型的完成文本直接视为验证成功。

明确区分三种恢复：手机重新连接、加载历史会话继续新回合、执行进程中断。首版保证前两者的交互与记录正确；进程中断后明确显示中断状态。

## 5. 6–8 周安排

- **第 1 周**：固定 Codex CLI 兼容版本，打通启动任务、接收事件、审批和中断。
- **第 2 周**：完成 Host 持久化、事件序号、快照及审批状态管理。
- **第 3–4 周**：完成 Android 时间线、差异查看、审批和本地缓存。
- **第 5 周**：完成断线恢复、后台恢复及阅读位置保持。
- **第 6 周**：完成自动回归和端到端演示，交付可安装版本。
- **第 7–8 周**：测量性能、修复边界问题，整理架构取舍与演示材料。

最终演示使用一个可重置的小型代码仓库，重复展示“启动修复 → 手机阅读 → 审批 → 断网重连 → 查看差异与测试结果”。

**保留 Runvori 这个名字，将首版定位定为“开发者离席后的 Codex 移动接管”。** 后续是否扩展，由这个场景中的实际需求决定。
