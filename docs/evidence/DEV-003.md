## 本轮行为

- 已知的 `item/commandExecution/requestApproval` 和 `item/fileChange/requestApproval` 可作为事件读出；即使请求先于 `turn/start` RPC 响应到达，也不会遗失。
- 调用方必须显式选择 `accept` 或 `decline`。同一请求 ID 只发送一次；不接受 `acceptForSession`、策略扩权和未知控制请求。写入超时后结果不确定，连接失效且不自动重发。
- 这只是顺序探针传输。已处理收到的上游请求结束通知；尚未持久化审批或实现生产级并发调度。
- 新增显式启用的执行探针：只能使用仓库 `.dev` 内带标记的空 Git 测试仓库；账号目录与审批决定是必填参数。固定受限工作区及逐次审批，按 `thread/start → turn/start → turn/completed → thread/resume` 采集事件形状和实际文件核对，报告不写上游字符串值。
- 真实拒绝审批路径观察到 `item/commandExecution/requestApproval`，传输层发送一次 `decline` 后收到 `serverRequest/resolved`，回合最终 `completed`，`thread/resume` 可识别原 thread；目标文件不存在、命令项退出码为 null。请求结束通知不证明批准生效或命令成功。脱敏形状夹具见 [JSON](DEV-003-command-declined.json)。
- 传输层在收到 `serverRequest/resolved` 后撤销尚未回复的审批，迟到的允许/拒绝均被拒绝；真实通知中的 `requestId` 为整数，合成回归覆盖该类型。
- 允许探针可选只读 `python --version`、固定 `Set-Content` 写入命令或固定输出标记后等待的中断命令；只对选定场景的完整命令及本机固定 Codex PowerShell 包装形式回复单次 `accept`。校验回合、命令、cwd 和权限字段；其他请求仍回复 `decline`，报告逐项记录实际决定，避免把 `--approval accept` 模式误读为所有请求均已允许。

该请求的 `grantRoot` 为 null，包含 thread、turn、item ID，却不直接包含补丁内容或目标路径；文件改动形状出现在邻近的 item 事件中。本轮未核对这些事件与审批请求的 item ID 是否相同。因此请求本身不能作为安全允许的充分依据，后续须核对关联 item 的路径和变更内容，且只发送本次 `accept`。本轮只验证拒绝与文件未落盘，尚未验证文件修改允许、写入结果或上游对 `grantRoot` 非空值的行为。`serverRequest/resolved` 只表示审批请求结束，回合 `completed` 不表示文件改动成功。

## 合成确认丢失故障注入

使用仓库的 JSONL 合成 peer，在收到一次文件审批 `accept` 后立即关闭连接，不发送 `serverRequest/resolved`。两个切点分别位于模拟副作用之前和之后：两者均确认 peer 收到恰好一次答复，Host 下一次读取均得到 `upstream_closed`，第二次尝试答复均被 `connection_unusable` 拒绝；两种情形的模拟副作用结果不同。脱敏结果见 [JSON](DEV-003-confirmation-lost-synthetic.json)。

因此“答复已写入管道、随后连接断开”不足以判断上游是否实施改动；调用方须保持结果不确定、禁止自动重发，并在恢复后按实际文件和上游记录核对。本测试只验证顺序传输层的失败关闭行为；它不是用真实 Codex 重现确认丢失，也未验证生产 Host 的持久化审批状态机或重启恢复。

关闭后核对测试仓库：目标文件不存在，目录只有初始标记和 Git 元数据，没有额外文件。`accepted_file_change_status=not_observed`、`turn_status=unknown`、`resume=not_attempted`；没有把管道写入或进程关闭当成上游确认、回合中断或审批生效。`close()` 包含短暂的协作退出等待，因此切点是“答复写入返回后立即请求关闭”，不是零延迟强杀。文件不存在也不能区分上游未收到答复、收到但尚未执行或执行被进程关闭打断。该场景不证明真实通知丢失、Host 重启恢复或持久化状态机。

## 真实完成后迟到中断

新建只含标记文件的可丢弃 Git 仓库，使用独立账号目录执行固定只读 `python --version`。唯一命令审批通过白名单并获一次 `accept`；零基事件索引 29 为审批、33 为同一命令 item 结束，真实退出码为 0，57 为 `turn/completed: completed`。只有在该终态已读到且命令退出码确认为 0 后，探针才发送一次 `turn/interrupt`。RPC 返回脱敏错误，记为 `rejected`；已观察到的回合终态仍为 `completed`。这次运行采用旧传输处理策略，RPC 错误后未尝试 `thread/resume`；后续传输已允许在匹配的 RPC 错误后继续读取。测试仓库没有新增目标文件。脱敏结构见 [JSON](DEV-003-late-interrupt-rejected.json)。

这是“完成终态先于中断请求”的确定顺序，不是完成和中断真正并发的竞争，也不能从脱敏 RPC 错误推断具体上游拒绝原因。它支持终态不可因迟到控制请求倒退的映射规则；产品 Host 在已知终态时应直接返回当前终态，不必发这个迟到 RPC。

## 真实命令完成后的中断时序

另用三个全新可丢弃仓库，均只允许固定只读 `python --version` 一次。探针读到对应命令 `item/completed` 且真实退出码 0 后，在尚未读取回合终态时分别立即、等待 1 秒、等待 5 秒发出 `turn/interrupt`，然后继续读取终态并恢复原 thread。立即与 1 秒切点：中断 RPC 返回，回合 `interrupted`；5 秒切点：RPC 返回脱敏错误，但传输继续读取到 `turn/completed: completed`，随后 `thread/resume` 识别原 thread。三个仓库均只有初始标记和 Git 元数据。脱敏结构、事件索引和各次结果见 [JSON](DEV-003-command-completion-interrupt-race.json)。

三个结果共同表明命令 item 的退出码 0 与整个回合终态是两种独立事实；中断 RPC 答复或错误也不能替代回合终态。5 秒切点的 `turn/completed` 虽在 RPC 之后才被探针读取，可能早已由上游生成并排队，因此不据此断言其实际生成时间或中断处理的精确并发顺序。这些切点覆盖了可观察的两种结局，仍不构成生产 Host 中断竞争验收。

`availableDecisions` 在真实命令审批消息中出现，但当前导出的对应 schema 未声明它；本版本映射需保留这条差异并在升级时复核。尚未验证上游精确并发顺序、Host 重启和真实 Codex 确认丢失。独立 SQLite 派发边界见 [记录](DEV-003-approval-journal.md)；下一步核对其余上游能力与 M0 兼容映射，不把探针外推到生产 Host 状态机。

## 本地 Git 重命名证据

在独立可丢弃仓库中，先提交两个固定内容文件作为基线。对其中一个执行 `git mv`，另一个仅用文件系统移动，不暂存。`git diff --cached --name-status -z --find-renames=100%` 对前者返回 `R100` 与原/新路径；未暂存差异对后者只返回原路径删除，`git ls-files --others -z` 报告新路径未跟踪。即使字节相同，也不把后者写成已确认重命名。探针校验固定夹具，任何预期文件被改动则拒绝出具报告；脱敏结果见 [JSON](DEV-003-rename.json)。此结果只说明 Git 本地视图，归因仍为 `unknown`；未观察 Codex 上游重命名事件。

## 真实文件移动审批拒绝

使用 Codex CLI `0.164.0-alpha.11.1`、独立已登录账号和新的可丢弃 Git 仓库。仓库先提交固定 `move-source.txt`，探针在 `read-only` 沙箱中要求仅用 `apply_patch` 将其移动到固定目标并改写一行。所有审批均拒绝。真实回合的零基事件索引 26 是文件改动 item 开始；其单一变更为 `update`，`move_path` 和原路径均匹配预定文件。索引 28 是一次文件审批，索引 29 为请求结束，31 为文件改动 item 结束，61 为回合 `completed`；原 thread 可恢复。没有命令审批或允许决定。结束后原文件字节不变、目标文件不存在，Git 状态为空。脱敏摘要见 [JSON](DEV-003-file-move-declined.json)。

该观察证明本版本上游至少可提出带 `move_path` 的文件改动审批；拒绝路径没有产生预定文件效果。`serverRequest/resolved` 和回合 `completed` 不证明移动成功，不能从此推断允许后操作的结果或适用于任意移动路径。后续固定允许案例见下节；Host 产物归因仍待验证。

## 真实固定文件移动单次允许

在新的可丢弃 Git 仓库中先提交同一固定源文件，仍使用独立账号和 `read-only` 沙箱。先以仅拒绝的临时本地诊断核对当前 CLI 提出的完整补丁格式；诊断脚本随即删除，未提交原始上游消息。正式探针只在单个 `fileChange` item 的源路径、目标 `move_path`、`update` 类型、完整一行替换补丁和源文件字节均精确匹配，且审批请求的 thread/turn/item 一致、`grantRoot` 为 null 时发送一次 `accept`。未知字段、额外变更和命令审批不会被允许。

## 真实固定二进制命令写入

在新的可丢弃 Git 仓库中先提交含 NUL 字节的固定 `binary.bin` 基线。模型被要求只运行一条精确的 Python 命令，将该文件改为 2,048 个固定二进制字节。首次真实请求因 PowerShell 把含内部双引号的命令另作双引号包装，白名单安全拒绝，文件未改。临时本地诊断只读出命令包装，确认正文仍是预定单文件写入后删除诊断脚本；白名单仅增加这一精确包装形式，附加命令和不同目标路径仍拒绝。
